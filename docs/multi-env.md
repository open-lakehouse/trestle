# Multiple environments on one host

Status: design, first slice in progress.

`trestle env new` renders one environment (one directory holding `env.toml`,
`compose.yaml` and the module fragments). This document covers running **several
environments side by side** on one Docker host, such as a `dev` and a `prod` that
start and stop independently, and the path from there to cross-environment
governance: separated networks, then workload identity with SPIFFE/SPIRE and
Envoy.

SPIRE is not part of this work. It is described here because it shapes the
decisions made now.

## What is already isolated

Each environment is its own Compose project. The head `compose.yaml` sets
`name:` to the environment name, so Compose scopes these per project:

| Resource | Why it does not collide |
|---|---|
| Network | No module declares `networks:`. Each project gets its own `<project>_default`. |
| Named volumes (`gateway-certs`, `postgres-data`, `rustfs-data`) | Prefixed with the project name. |
| Container names | Generated by Compose (except an explicit Unity Catalog `container_name` knob). |
| Gateway CA | Minted into the project's own `gateway-certs` volume, so each env has its own CA. |
| Secure origin (`<env>.localhost`, `<env>.internal`) and the Authelia cookie domain | Derived from the env name. |
| Hosted resource names (`trestle-<env>`) | Derived from the env name. |
| Bind mounts | Under `DATA_ROOT`, by default `./.data` relative to each env directory. |

## What collides today

| Collision | Cause | Resolution |
|---|---|---|
| Same env name | Two directories with one `name:` silently share a Compose project. | Names must be unique within a workspace. The Compose project becomes `<workspace>-<env>`. |
| Gateway `9080` | `PlanCtx::gateway_host_port` default. | The workspace assigns per-env ports. |
| Envoy admin `9901` | `PlanCtx::gateway_admin_port` default, published 1:1. | The workspace assigns per-env ports. |
| Dedicated listeners `9100+` | `PlanCtx::dedicated_listener_port_base` default (RustFS `s3`, UIs that only serve `/`). | The workspace assigns a per-env base. |
| Module-declared host ports (PuppyGraph Bolt `7687` and Gremlin `8182`; direct ports with `--no-gateway`) | Declared by the module or taken from the container port. | A per-env `port_offset` shifts every module-declared host port. |
| Shared absolute `--data-root` | Two envs would mount the same directories. | Keep the default relative root. The workspace never shares one. |
| Default credentials | `LOCAL_CREDENTIALS` defaults are identical in every env. | Not a port problem, but a "prod" env should get its own `secrets.env`. |

The planner checks port conflicts only inside one environment. Nothing looks
across environments.

## The workspace

A **workspace** is a directory holding a `trestle-workspace.toml` and one
subdirectory per member environment:

```text
demo/
├── trestle-workspace.toml
├── dev/      # a normal env directory: env.toml, compose.yaml, modules/, …
└── prod/
```

```toml
version = 1
name = "demo"
mesh = true

[[envs]]
name = "dev"
path = "dev"
slot = 0

[[envs]]
name = "prod"
path = "prod"
slot = 1
```

Each member stays self-contained. `docker compose up` inside `demo/prod` works
without the workspace, because everything the workspace decides is written into
that env's `env.toml`. The workspace only allocates those values and checks them.

### Slots and ports

Each env gets a **slot**. Slot `n` shifts every host port the env publishes by
`n × 1000`:

| | slot 0 | slot 1 | slot 2 |
|---|---|---|---|
| Gateway | 9080 | 10080 | 11080 |
| Envoy admin | 9901 | 10901 | 11901 |
| Dedicated listeners | 9100+ | 10100+ | 11100+ |
| PuppyGraph Bolt | 7687 | 8687 | 9687 |

Slot 0 keeps today's ports, so a single env, or the first member of a workspace,
is unchanged.

The gateway, admin and dedicated-listener ports are absolute values in
`[context]`, as they are today (and dedicated ports stay pinnable with
`pin_dedicated_ports`). The workspace writes the slot's values there. Host ports
that a module declares itself have no context field, so `[context] port_offset`
shifts them instead. That covers PuppyGraph's Bolt and Gremlin ports, Jaeger's
OTLP port, and every direct publish without a gateway.

After rendering, the workspace collects each plan's host ports
(`Plan::host_ports`) and rejects any overlap across members. That catches a
hand-edited `env.toml` drifting into a neighbour's range.

### Project names

`[context] project_name` overrides the Compose `name:`. The workspace sets it to
`<workspace>-<env>` (`demo-dev`, `demo-prod`), so two workspaces that both have a
`dev` never share containers or volumes. Hostnames keep using the env name
(`dev.localhost`).

Known limit: browsers scope cookies by host, not port. Two workspaces that both
have a `dev` share the `dev.localhost` sign-in cookie, so run one at a time or
pick distinct names.

## Networks

The network plan comes in three phases. Each phase keeps the next one open.

1. **Private per env (today).** Each project has its own default network.
   Services in `dev` cannot reach `prod` at all.
2. **Gateway mesh (this work).** With `mesh = true`, every member's gateway, and
   only its gateway, also joins a shared network `trestle-<workspace>-mesh`
   under the alias `<env>.mesh`. Cross-env traffic therefore has exactly one
   entry and one exit per environment: its Envoy. Workloads stay on their
   private network. The network is declared with a fixed `name:` rather than
   `external: true`, so whichever env starts first creates it and no separate
   setup step is needed.
3. **Workload identity (later).** A workspace-level **platform** stack (its own
   Compose project in the workspace, on the highest slot) runs the SPIRE root
   server on the mesh. Each env runs a nested SPIRE server, chained to the root,
   plus an agent. Envoy fetches its SVID and trust bundle over SDS from the
   agent and does mTLS on a mesh listener. Envoy RBAC (or the existing OPA
   policy hook) then authorizes by SPIFFE ID. That enables policies like "prod
   accepts reads from dev's catalog, never writes".

   Two trust models are left open:
   - One trust domain per workspace with per-env path prefixes
     (`spiffe://demo/env/prod/…`). The hierarchy is in the SPIRE server chain,
     which is simpler to start with.
   - One trust domain per env, federated. Closer to real cross-organisation
     setups, at more configuration cost.

Choices made now with phase 3 in mind:

- Only gateways join the mesh, so the mesh listener is the single place mTLS
  goes later.
- The workspace manifest is where shared, workspace-scoped resources (the mesh
  network, later the platform stack) are declared. Env manifests stay free of
  cross-env knowledge.
- Project names carry the workspace, so a platform project (`demo-platform`)
  fits the same scheme.

## CLI

```bash
trestle workspace init demo --mesh
trestle workspace add dev -y            # same flags as `trestle env new`
trestle workspace add prod -y
trestle workspace list
trestle workspace render                # re-render every member, then check for conflicts
trestle workspace up [ENV…]             # docker compose up -d --wait, per env
trestle workspace down [ENV…]
trestle workspace status
```

`trestle env new` and `trestle env render` inside a workspace member apply the
workspace's values, so the member keeps its slot.

## Editor

The environment editor becomes a workspace editor, laid out like an IDE
(Zed, VS Code):

- an activity bar
- an explorer listing the workspace's environments
- editor tabs, one per open environment or file
- a bottom panel with Problems (plan errors, cross-env conflicts) and Output
- a status bar

The editor never assumes where a workspace lives. It talks to an injected
`WorkspaceStore`, the same way it talks to an injected `Planner`. The first store
keeps workspaces in `localStorage`. The interface is async, so a store backed by
the File System Access API, or by a local `trestle workspace serve` HTTP server,
can replace it without touching the editor. Downloading a workspace produces the
same layout the CLI uses, so a browser-made workspace renders with
`trestle workspace render`.
