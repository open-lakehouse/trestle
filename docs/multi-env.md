# Multiple environments on one host

Status: workspaces, environments, revisions and instances live in the trestle
state store (`olai-stack-state`) and the CLI runs on it (`trestle ws`, `env
create`/`commit`, `var`, `up`/`down`/`ps`). Slots, the gateway mesh
(`mesh = true`) and the workspace editor have landed. The directory-based
`trestle workspace` commands are deprecated; see the migration note below.
Phase 3 (SPIRE workload identity, below) is design only.

`trestle env new` renders one environment (one directory holding `env.toml`,
`compose.yaml` and the module fragments). This document covers running **several
environments side by side** on one Docker host, such as a `dev` and a `prod` that
start and stop independently, or two revisions of one environment, and the path
from there to cross-environment governance: separated networks, then workload
identity with SPIFFE/SPIRE and Envoy.

SPIRE is not part of the implemented work. It is described here because it shapes
the decisions made now.

## What is already isolated

Each environment is its own Compose project. The head `compose.yaml` sets
`name:` to the environment name, so Compose scopes these per project:

| Resource | Why it does not collide |
|---|---|
| Network | No module declares `networks:`. Each project gets its own `<project>_default`. |
| Named volumes (`gateway-certs`, `postgres-data`, `rustfs-data`) | Prefixed with the project name. |
| Container names | Generated by Compose (except an explicit Unity Catalog `container_name` knob). |
| Gateway CA | Minted into the project's own `gateway-certs` volume, so each env has its own CA. |
| Secure origin (`<label>.localhost`, `<label>.internal`) and the Authelia cookie domain | Derived from the host label: the env name on its own, `<workspace>-<env>-r<n>` for an instance. |
| Hosted resource names (`trestle-<env>`) | Derived from the env name. |
| Bind mounts | Under `DATA_ROOT`, by default `./.data` relative to each env directory. |

## What collides between environments

| Collision | Cause | Resolution |
|---|---|---|
| Same env name | Two directories with one `name:` silently share a Compose project. | Names are unique within a workspace, and an instance's Compose project is `<workspace>_<env>_r<n>`. |
| Gateway `9080` | `PlanCtx::gateway_host_port` default. | Each instance's slot shifts its ports. |
| Envoy admin `9901` | `PlanCtx::gateway_admin_port` default, published 1:1. | Each instance's slot shifts its ports. |
| Dedicated listeners `9100+` | `PlanCtx::dedicated_listener_port_base` default (RustFS `s3`, UIs that only serve `/`). | Each instance's slot shifts the base. |
| Module-declared host ports (PuppyGraph Bolt `7687` and Gremlin `8182`; direct ports with `--no-gateway`) | Declared by the module or taken from the container port. | A per-env `port_offset` shifts every module-declared host port. |
| Shared absolute `--data-root` | Two envs would mount the same directories. | Keep the default relative root. The workspace never shares one. |
| Default credentials | `LOCAL_CREDENTIALS` defaults are identical in every env. | Not a port problem, but a "prod" env should set its own (`trestle var set --secret`). |

The planner checks port conflicts only inside one environment. Nothing looks
across environments.

## The workspace

A **workspace** is a set of environments sharing the Docker host, the vars they
all see, and whether their gateways share a mesh network. It lives in the state
store: one SQLite database under `$TRESTLE_HOME` (by default `trestle` in the
platform data directory), which the CLI and the desktop app share.

```text
Workspace ─┬─ vars, mesh, source config
           └─ Environment ─┬─ draft (env.toml + module.yaml texts + vars), vars, head
                           └─ Revision n (immutable)
Instance = a revision to run ─── SlotLease (host-wide)
```

- An environment's **draft** is what its next revision will be. `env
  add-module`, `remove-module` and `set-knob` edit it, and every edit is checked
  by planning the draft. `env commit` freezes it as the next numbered
  **revision**, which nothing changes afterwards.
- An **instance** runs one revision. `trestle up demo/dev` runs the head and
  `up demo/dev@2` runs revision 2. Two revisions of one environment run side by
  side, each on its own slot, project and host label.
- **Vars** come in three scopes, picked by the target: `trestle var set demo`
  sets the workspace's (every environment sees them), `var set demo/dev` the
  environment's (every revision sees them), and `var set demo/dev --draft` the
  draft's (frozen into the next revision). With `--secret` the value goes to the
  OS keychain, read from stdin and never from the command line, and the store
  keeps only a reference to it. Each revision's draft secrets get keychain keys
  of their own, so editing the draft never changes what a committed revision
  resolves to.

An instance's environment is layered, lowest precedence first: catalog defaults,
the revision's manifest, the placement (reserved keys nothing overrides), the
plan's client env, workspace vars, environment vars, revision vars, source
overlays, then instance overrides. `trestle env show <ws>/<env>@<n> --effective`
prints every variable with the layer it comes from, secrets masked. See
[`runtime.md`](runtime.md).

What an instance gets from where it runs is its **placement**
(`RuntimePlacement { slot, project_name, mesh_network, host_label }`), not part
of the environment. The revision's `env.toml` never records it (manifest
version 5), which is what lets one revision be placed twice. A version-4
`env.toml` still reads: its `project_name`, `mesh_network` and `port_offset` are
dropped, and its slot-shifted ports move back to slot 0.

### Slots and ports

Each instance leases a **slot**, host-wide: the store hands out the lowest slot no
instance on the host holds, whatever its workspace, so two workspaces never
clash. Slot `n` shifts every host port the instance publishes by `n × 1000`:

| | slot 0 | slot 1 | slot 2 |
|---|---|---|---|
| Gateway | 9080 | 10080 | 11080 |
| Envoy admin | 9901 | 10901 | 11901 |
| Dedicated listeners | 9100+ | 10100+ | 11100+ |
| PuppyGraph Bolt | 7687 | 8687 | 9687 |

Slot 0 keeps the single-environment ports. The lease stays with the instance
until it is removed (`trestle down --rm`), so a restarted instance keeps its
ports.

The gateway, admin and dedicated-listener ports in `[context]` are the env's own,
slot-0 values (dedicated ports stay pinnable with `pin_dedicated_ports`). The
placement shifts them by the slot's offset, so an environment that sets its own
gateway port keeps it, shifted, on any slot. Host ports that a module declares
itself have no context field, so the planner's `port_offset` shifts them
instead. That covers PuppyGraph's Bolt and Gremlin ports, Jaeger's OTLP port, and
every direct publish without a gateway. `trestle up` checks the instance's host
ports before starting it.

### Project names and host labels

An instance's Compose project is `<workspace>_<env>_r<n>` (`demo_dev_r2`). Trestle
names can't contain `_`, so a project name parses back to its parts, and the
store and Docker can be reconciled after a crash. Two workspaces that both have
a `dev` never share containers or volumes, nor do two revisions of one
environment.

The host label is `<workspace>-<env>-r<n>`, so an instance's hostnames are
`demo-dev-r2.localhost` and `demo-dev-r2.internal`. Browsers scope cookies by
host, not port, so this is what keeps two instances from sharing a sign-in
cookie. An env rendered on its own keeps its name as the label (`dev.localhost`).
Hosted resource names (`trestle-<env>`) keep following the env name.

### Workspace directories

`trestle-workspace.toml` and environment directories are the exchange format:

```text
demo/
├── trestle-workspace.toml
├── dev/      # a normal env directory: env.toml, module manifests, …
└── prod/
```

```toml
version = 1
name = "demo"
mesh = true

[[envs]]
name = "dev"
path = "dev"
slot = 0

[[envs]]
name = "prod"
path = "prod"
slot = 1
```

`trestle ws import <dir>` creates the workspace from such a directory, each
member's `env.toml` (and the module manifests it lists) committed as revision 1.
Slots are not imported, because the store leases its own, and neither is
`secrets.env`, because the store holds references, not values. `trestle ws
export <ws> <dir>` writes each environment's head back out, on the slot an
instance of it holds or the lowest free one, so `trestle env render` and
`docker compose up` work in the exported directory. `trestle env export
<ws>/<env>@<n> <dir>` writes one revision as an environment directory.

### Migrating from `trestle workspace`

The directory-based `trestle workspace init/add/remove/list/render/up/down`
commands still work and print a deprecation warning. To move a workspace into the
store:

```bash
trestle ws import ./demo                  # each member becomes revision 1
printf %s "$PG_PASSWORD" | trestle var set demo/prod --secret PG_PASSWORD
trestle up demo/prod                      # was: trestle workspace up prod
trestle ps                                # was: trestle workspace list
trestle down demo                         # was: trestle workspace down
```

Projects started by `trestle workspace up` are named `<workspace>-<env>`, and
instances `<workspace>_<env>_r<n>`. Take the old ones down with
`trestle workspace down` before starting the imported workspace, since they hold
the same ports. Values from `secrets.env` need setting again as vars, with
`--secret` for the sensitive ones.

## Networks

The network plan comes in three phases. Each phase keeps the next one open.

1. **Private per env (the default).** Each project has its own default network.
   Services in `dev` cannot reach `prod` at all.
2. **Gateway mesh (implemented).** With `mesh = true`, every member's gateway, and
   only its gateway, also joins a shared network `trestle-<workspace>-mesh`
   under the alias `<label>.mesh` (`demo-prod.mesh`). Cross-env traffic therefore has exactly one
   entry and one exit per environment: its Envoy. Workloads stay on their
   private network. The network is declared with a fixed `name:` rather than
   `external: true`, so whichever env starts first creates it and no separate
   setup step is needed. `trestle down` removes it once no instance of the
   workspace runs.
3. **Workload identity (later).** A workspace-level **platform** stack (its own
   Compose project in the workspace, on the highest slot) runs the SPIRE root
   server on the mesh. Each env runs a nested SPIRE server, chained to the root,
   plus an agent. Envoy fetches its SVID and trust bundle over SDS from the
   agent and does mTLS on a mesh listener. Envoy RBAC (or the existing OPA
   policy hook) then authorizes by SPIFFE ID. That enables policies like "prod
   accepts reads from dev's catalog, never writes".

   Two trust models are left open:
   - One trust domain per workspace with per-env path prefixes
     (`spiffe://demo/env/prod/…`). The hierarchy is in the SPIRE server chain,
     which is simpler to start with.
   - One trust domain per env, federated. Closer to real cross-organisation
     setups, at more configuration cost.

Choices made with phase 3 in mind:

- Only gateways join the mesh, so the mesh listener is the single place mTLS
  goes later.
- The workspace manifest is where shared, workspace-scoped resources (the mesh
  network, later the platform stack) are declared. Env manifests stay free of
  cross-env knowledge.
- Project names carry the workspace, so a platform project (`demo-platform`)
  fits the same scheme.

## CLI

```bash
trestle ws create demo --mesh
trestle env create demo/dev --select unity-catalog,mlflow   # a draft
trestle env set-knob demo/dev mlflow.log_level=debug
trestle env commit demo/dev                                 # r1
trestle var set demo/dev LOG_LEVEL=info
printf %s "$TOKEN" | trestle var set demo/dev --secret TOKEN
trestle up demo/dev                     # the head; `demo/dev@1` for a revision
trestle ps
trestle health demo/dev
trestle logs demo/dev -f
trestle env show demo/dev@1 --effective
trestle env diff demo/dev               # head → draft
trestle down demo/dev [--volumes] [--rm]
trestle ws export demo ./demo
```

Every read command takes `--json` and prints `{"version": 1, "kind": …, "data":
…}`: `ws list`, `ws show`, `env show`, `env revisions`, `var list`, `ps` and
`health`. `env new`, `env render` and `env diagram` keep working on directories.

## Editor

The environment editor becomes a workspace editor, laid out like an IDE
(Zed, VS Code):

- an activity bar
- an explorer listing the workspace's environments
- editor tabs, one per open environment or file
- a bottom panel with Problems (plan errors, cross-env conflicts) and Output
- a status bar

The editor never assumes where a workspace lives. It talks to an injected
`WorkspaceStore`, the same way it talks to an injected `Planner`. The first store
keeps workspaces in `localStorage`. The interface is async, so a store backed by
the File System Access API, or by the trestle state store behind a local HTTP
server, can replace it without touching the editor. Downloading a workspace
produces the workspace directory layout, so a browser-made workspace imports with
`trestle ws import`.
